The Layer Below Agents: Why We Need an Agentic Organization Runtime

W.Y.2026-07-24

1. The Blind Spot

2026 has been a busy year for agents.

  • Alibaba Cloud released ANOLISA, an agent-native Linux with kernel-level optimizations for LLM workloads.
  • Sakana AI launched Fugu, a multi-model routing system that dynamically selects the best model for each task.
  • StepFun announced Step AOS, a mobile OS built from the ground up for on-device agents.
  • OpenAI shipped voice mode for Codex, turning it into a conversational coding agent.
  • Cerebras doubled down on AI inference hardware, driving down latency and cost.

Everyone is making agents smarter, faster, and cheaper. Better models, lower latency, richer tool ecosystems, stronger safety guarantees — the progress is real.

But I kept noticing a question that no one seems to be asking:

When you have 50 agents working on a complex project, who organizes them?

A 50-person team is not 50 individuals working in isolation. It has a structure: managers who break down work, leads who coordinate, engineers who execute, reviewers who validate, communication channels, governance rules, and shared memory. The structure is what makes the team more than the sum of its parts.

Agents have the same problem. A pool of 50 independent agents, each pointing at a different LLM, each with a different tool set, does not constitute a team. It constitutes a crowd.

I don't think anyone has a good answer to this yet. So I've been trying to build one.

2. The Missing Layer

The current AI stack has a gap.

┌───────────────────────────────────────────────┐ │ Application Layer │ │ Codex, QoderWake, Agent 365, StepAmoo, etc. │ ├───────────────────────────────────────────────┤ │ ─── THIS LAYER IS MISSING ─── │ ├───────────────────────────────────────────────┤ │ Orchestration Layer │ │ CrewAI, LangGraph, AutoGen │ ├───────────────────────────────────────────────┤ │ Model Routing Layer │ │ Fugu, LiteLLM, Portkey │ ├───────────────────────────────────────────────┤ │ OS Layer │ │ ANOLISA, Step AOS, Linux, macOS │ └───────────────────────────────────────────────┘

Between the orchestration frameworks (CrewAI, LangGraph) and the application layer (Codex, QoderWake), there is no layer that handles organization — the structuring of agents into teams with defined roles, communication protocols, governance policies, and shared memory.

I've been calling this missing layer the Agentic Organization Runtime (AOR). I'm not sure if this is the right name yet, but the gap it describes is real.

An AOR doesn't care which model an agent uses. It doesn't care what task an agent is executing. It cares about:

  • Structure: How agents are organized into teams with hierarchies and communication lines.
  • Coordination: How work is decomposed, dispatched, and tracked across agents.
  • Governance: What each agent is allowed to do, under what conditions.
  • Memory: What the organization collectively knows, across individual agent lifetimes.
  • Resilience: How the organization handles failures — API outages, rate limits, network errors.
  • Design: How users define and modify the organization structure — through a visual canvas, not code.

The closest analogy I've found is Kubernetes. Kubernetes doesn't care what application you run — it cares about scheduling, scaling, networking, and fault tolerance. An AOR doesn't care what task your agents execute — it cares about how they are organized, how they communicate, and how they recover from failure.

3. The Architecture: Three Roles, Four Systems

I want to be clear: this is not a finished design. It's what I've arrived at after a lot of trial and error, and it will likely change. But here's where it stands today.

An AOR has three structural roles and four supporting systems.

Three Roles

Director — The overseer. The Director sits outside the organization, maintains a global view, and communicates with the user through natural language. It monitors the organization's state, reports anomalies, analyzes problems, and executes user decisions. It can create or destroy any Manager or Operator, adjust policies, and intervene when necessary.

Manager — The coordinator. The Manager receives a high-level task, decomposes it into subtasks, creates Operators with appropriate capabilities, dispatches work, tracks progress, and stores results in the Archive. Managers can recursively manage other Managers — a Manager does not need to know the details of how a sub-Manager coordinates its Operators.

Operator — The executor. Each Operator has a defined capability boundary (tool set, read/write permissions, model binding), and autonomously decides how to complete its assigned task. It is not a fixed-script executor — it understands intent and self-determines the execution path.

Four Systems

Policy — Governance layer. Defines what each Operator is allowed to do, under what conditions. Policies are dynamic: they can be overridden for specific tasks, escalated to the Director for approval, or hardened for sensitive operations.

Channel — Communication infrastructure. Operators and Managers communicate through Channel, not direct function calls. This decouples senders from receivers and enables message routing, broadcast, and audit logging.

Archive — Organizational memory. Every task result, every decision, every error is stored in the Archive. The Archive is not a simple log — it is a structured knowledge base that Managers and the Director can query to inform future decisions.

Selector — Model selection strategy. Not all tasks should go to the same model. The Selector evaluates each task against multiple factors — capability requirements, latency sensitivity, cost constraints, past success rates — and chooses the optimal model. The Selector's decisions are recorded and fed back to refine future selection weights, creating a self-improving loop.

The Data Loop

What makes these components work together is not their individual capabilities — it is the closed loop between them:

User intent → Director interprets → Manager decomposes → Selector chooses model → Operator executes → results stored in Archive → Manager evaluates → feedback to Director → Director reports to user → loop continues

Every layer's output is another layer's input. Change any layer, and the others adapt.

4. Experimental Validation

I've been running a series of experiments on a custom Go engine to test whether this architecture actually works. The results so far have been encouraging, but I want to be upfront about what's been tested and what hasn't.

Hierarchical Coordination

The experiment ran with 2 Managers coordinating 12 Operators — not a flat pool, but a hierarchical structure. One Manager focused on data layer tasks, the other on business logic. This is not a limitation of the system but a design choice: Managers can recursively manage other Managers, so in principle an organization can scale through hierarchy rather than flat parallelism. I haven't tested this beyond two layers yet.

Cross-Model Collaboration

Operators in the same organization can be bound to different LLMs. One Operator may use Claude for reasoning, another GPT for creative generation, a third Gemini for long-context retrieval, and a fourth Qwen for Chinese-language understanding. All four collaborate within the same organization structure, coordinated by the Manager.

This is not a demo of multi-model routing. It is a demo of multi-model teamwork. That said, I should note that making different models work together smoothly required a fair amount of plumbing — it's not plug-and-play yet.

Resilience

Before the resilience layer was active, 14 concurrent requests would trigger 429 rate limits from the API provider, causing the entire organization to stall. After implementing the four-tier resilience strategy — retry, backoff, circuit breaking, and provider failover — zero 429 errors were observed at the same concurrency level.

I also hit a fairly embarrassing bug: SSE streams returning HTTP 200 with embedded event: error were being silently swallowed. The system was "succeeding" at the transport layer while failing at the application layer — which is why my resilience layer never triggered for so long. After the fix, SSE errors are properly detected, triggering retry (5s → 10s → 20s → 60s backoff), graceful degradation, and notification to the Director.

What Has Not Been Tested

I want to be honest about the gaps:

  • 50+ Operators running concurrently — I expect the bottleneck to be Channel capacity, but I don't know yet.
  • Multi-tenant isolation — multiple organizations running on the same engine is untested.
  • Long-running organizations — everything so far has been minutes, not hours or days.

These are the next experiments on my list.

5. Why This Layer Can Only Be Built by a Neutral Player

This is the part where I'm most confident, because it's not about my engineering — it's about structural incentives.

The largest AI companies cannot build an AOR. This is not a technical limitation — it is a structural one.

  • OpenAI's incentive is to keep users inside the GPT ecosystem.
  • Google's incentive is to keep users inside the Gemini ecosystem.
  • Alibaba's incentive is to keep users inside the Qwen ecosystem.
  • StepFun's incentive is to keep users inside the Step model ecosystem.

A cross-model organization runtime, by definition, requires neutrality. It must be able to route a task to Claude, GPT, Gemini, or Qwen based on what is best for the task, not based on what is best for the platform provider. No major AI company can make this commitment — not because they lack the talent, but because their business model won't let them.

This is the same structural constraint that made Kubernetes emerge from a neutral foundation rather than from any single cloud provider. AWS could have built a container orchestration system — and it did, in the form of ECS — but it could never have built a system that treats AWS, GCP, and Azure as equal peers. Kubernetes did, because Kubernetes had no incentive to favor any one cloud.

I'm not claiming the AOR is Kubernetes. But I think the structural parallel holds: a neutral runtime layer that treats all providers as interchangeable resources is something only a neutral player can build.

Atomic Recomposition

Here is a concrete way to think about what this enables:

Every agent product on the market — Codex, QoderWake, Agent 365 — is a bundled organization configuration. Codex is a "coding team" template. QoderWake is a "digital employee management" template. Agent 365 is an "enterprise governance" template.

If the AOR works as intended, these bundles become templates that users can load, mix, and recombine. A user could take QoderWake's DevOps Operator, combine it with Codex's coding Operator, add a custom testing Operator, and run them under a single Manager with a unified Policy.

No product vendor can offer this, because no vendor wants you to mix their agent with a competitor's. Only a neutral runtime can.

6. What's Next

The engine is currently in private testing. I'm planning to open-source the core in the coming months, once I've cleaned up a few more rough edges.

If this direction interests you — whether you want to build your own agentic organization, contribute templates, or just poke holes in the architecture — here are the open problems I'm currently grappling with:

  1. Scaling: How does the Channel system behave under 50+ concurrent Operators? I honestly don't know where the bottleneck is yet.
  2. Governance: How do you define a Policy language that is expressive enough for complex workflows but simple enough for non-technical users? I don't have a good answer.
  3. Learning: Can the Manager learn from its own dispatch history to improve future task decomposition — independent of the Selector's model selection optimization? This is speculative at this point.
  4. Long-running organizations: What happens when an organization runs for days, accumulating Archive entries, evolving its structure, and adapting to changing task priorities? I haven't tested this at all.

I don't have all the answers. I'm not sure anyone does yet. But I think the question — how do you organize agents into a team — is one that the industry is going to have to answer sooner or later.

The goal isn't to build a better agent. The goal is to figure out a better way to organize them.

If you're working on similar problems, I'd love to talk.
