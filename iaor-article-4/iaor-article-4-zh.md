# 协同是怎么发生的：一次多智能体并行交付的全程复盘

**作者**: W.Y.
**日期**: 2026-08-12

---

## 一、一次让我想展开的协同

> 在整理前面几篇用到的那些数据时，我最想展开的其实是三个成员之间的协同——没想上升到什么宏大理论，就是觉得他们的协同方式有趣，于是把整个协同过程完整整理了一遍。这篇就是那次协同的复盘。

三个成员——一个 Manager 和两个 Operator，各自持有一条独立的模型连接，被组织成一个团队，去做一个 25 文件的 React 应用。6 分 26 秒，零冲突，`npm run build` 一次通过。

这篇不讲那个漂亮的数字，讲数字背后的过程：这三个成员，在什么时机，对谁，做了什么，为什么。素材来自这次运行的通信记录、事件时间线和运行截图。

先交代背景：

- **拓扑**：1 Manager + 2 Operator，全连接（Manager↔004、Manager↔003、004↔003）
- **分工**：004 负责 5 个基础设施文件（types/constants/utils/api/store），003 负责 20 个前端文件
- **前提**：三个成员各自独立连接一条 LLM API Key，不是单模型并发子代理
- **任务**：TaskFlow 看板应用，一份产品简报，目标 25 个文件

整个协同过程，可以拆成五幕。

## 二、第一幕：Manager 先把依赖关系前置解决（T+0 ~ 57 秒）

Manager 收到简报后，没有急着分派。它先读简报、读项目脚手架——`src/` 是空的、依赖已装好、技术栈是 React 19 + TypeScript + Zustand + Vite。

然后它做了一次任务拆解，一次决定整场协同成败的拆解：

- 25 个文件，5 个给 004（基础设施），20 个给 003（前端）
- 判定：两者可以并行
- 决策：把 004 的接口签名直接写进 003 的任务描述里

最后这一点是关键。003 依赖 004 的 types 和 store——照理应该先让 004 写完，003 才能开始。但 Manager 选择了**把依赖关系前置解决**：它把 004 会产出的接口签名，预先填进 003 的任务书里。于是 003 不需要等 004，两个 Operator 同时开工。

还有一个隐性的归属决策。简报里 constants.ts 被描述成"多个组件共同引用的共享文件"，没有说谁建。Manager 没有让两个 Operator 去协商，而是直接从技术架构判断——它是基础设施层文件——分给了 004。用"明确归属"代替"让成员协商"，这是第一处降低协同成本的决策。

## 三、第二幕：两个 Operator 并行，互不干扰（T+57 秒 ~ 3 分钟）

派发后，两个 Operator 各自开始。004 按依赖顺序分三批，21 秒内建完 5 个基础设施文件。003 在开始写组件前，做了一件小事：它主动读了 004 已经创建的 types.ts 和 constants.ts，确认实际接口和 Manager 预填的一致。

这个细节值得注意。003 信任 Manager 给的签名，但它还是自己去读了真实文件验证。信任但验证——这是协同里一种健康的态度：不因为"上级说了"就盲信，也不因为"已经验证过"就不管。

接下来两分钟里，两个 Operator 各写各的文件：003 建组件（每批 4 个文件），004 尝试验证自己的代码。它们之间没有任何消息往来，也完全不需要——因为各自的任务边界和接口契约已经在前一幕定死了。零冲突不是靠"边写边沟通"达成的，而是靠"开工前边界已清"达成的。

## 四、第三幕：第一次对等交接（T+3 分钟，004 → 003）

004 写完并验证完自己的 5 个文件后，做了一个**没人要求它做**的动作：它主动给 003 发了一条消息，把完整的接口文档交了出去。

通信记录里，这条消息是这样说的：

> "All 5 infrastructure files are created and type-checked. Here's what you need to know for building your components: ## 1. src/types.ts — Your import source for all types..."

它没有经过 Manager。004 判断 003 需要这些接口才能正确编码——虽然 Manager 在派发时已经给 003 预填了签名，但 004 不知道这一点。它从自己的角度判断"下游需要这个"，然后直接交给了下游。

这是一个被职业本能驱动的协同动作：不等人来问，主动把别人需要的东西送过去。通信对象由技术依赖决定——004 的接口被 003 消费，所以 004 通知 003。不需要请示，不需要 Manager 中转。

## 五、第四幕：一个缺口，Manager 主动补位（T+3 分钟 ~ 5 分钟）

就在这时，出现了一个问题。003 在创建组件时，漏掉了 TaskCard.tsx——它在 Manager 的任务清单里，但实际没有落盘。

发现这个问题的不是 003，也不是任何人的汇报，而是 Manager 自己。Manager 在派发后没有坐等，而是一直主动读文件、查状态。在 23:03:19 读取 TaskCard.tsx 时，它发现文件不存在——被 TaskColumn 依赖，却是空的。

Manager 没有先问 003"你是不是漏了"，而是直接 dispatch_task，把一份带完整规格的补写任务发给了 003：

> "CRITICAL MISSING FILE: Create src/components/TaskCard.tsx and src/components/TaskCard.css..."

这一点值得验证：在 23:01:11 派发之后、23:03:42 补派之前，Manager 没有收到任何 Operator 的消息。它完全是自己读文件时发现缺口的。这是"主动监督"——不等汇报、自己验证、发现问题自己补。

003 收到后重写了 TaskCard（5,636 字节），遇到两个 TypeScript 错误，自己逐一修复，然后 `npm run build` 通过。

## 六、第五幕：集成闭环与双重验证（T+5 分钟 ~ 完成）

003 的 build 通过后，做了两个动作，顺序很有意思：

1. 先向 Manager 汇报："Build SUCCESS ✅ 53 modules, 0 errors"
2. 再向 004 发一条消息："All 20 frontend files are built and compiling cleanly against your infrastructure..."

第二条不是 Manager 要求的。003 的判断是"004 需要知道集成结果"——因为 004 之前把接口交给了它，它在做闭环反馈。你告诉了我接口，我告诉你集成成功了。

这是一个社交性的闭环：一条向下的交接，配一条向上的确认。而 Manager 从头到尾不知道这两条对等消息的存在。

004 收到 003 的集成确认后，没有直接汇报收工。它又跑了一轮验证——7 次命令，包括 cache hit、命令格式报错，最终 `tsc --noEmit --pretty` 零错误。确认无误后，才向 Manager 汇报。

两个 Operator 在最终汇报前都做了"再验证一次"：003 在 build 成功后又跑了一次，004 更谨慎，跑了 7 次。它们都不想汇报了"完成"之后被打脸。

## 七、通信全景：协同靠的是稀疏而精准的消息

现在把整场协同的实质通信摆在一张表里——一共 5 条：

| 时间 | 发送者 | 接收者 | 类型 | 内容 |
|------|--------|--------|------|------|
| T+3min | 004 | 003 | inform | 5 个基础设施文件完整接口文档 |
| T+4min | Manager | 003 | request | 请运行 npm run build 并报告结果 |
| T+6min | 003 | Manager | response | Build SUCCESS，53 modules，0 errors |
| T+6min | 003 | 004 | inform | 20 个前端文件集成确认 |
| T+7min | 004 | Manager | inform | 5 个基础设施文件验证通过 |

25 个文件、零冲突、一次通过，全程实质通信只有 5 条消息。

而且这 5 条消息呈现清晰的两层结构：

- **指令-汇报层**（Manager ↔ Operator）：Manager 派发、请求，Operator 汇报结果，共 3 条
- **对等协同层**（Operator ↔ Operator）：004 交接口、003 回确认，共 2 条，Manager 从未参与

消息的发送对象不是随机选择的——全部由技术依赖关系决定：004 的接口被 003 用，所以 004 发给 003；003 的集成结果取决于 004 的接口，所以 003 回给 004。没有一条寒暄，没有一条"你还在吗"的确认，每一条都承载了对方真正需要的信息。

## 八、一个贯穿全程的行为：Manager 从不 idle

回看这次运行，有一样东西几乎被那个"25 个文件、零冲突"的数字盖住了：**Manager 从派发完的那一刻起，就没有停下来过。**

它一直在调用工具：读文件（read_file 62 次）、查目录（list_dir 18 次）、查两个 Operator 的状态（查询类工具 14 次）。直到最后所有任务完成，它才停下。它不是偶尔看一眼，而是全程醒着。

为什么会这样？因为这是一个主动验证型的管理者——它不等 Operator 汇报，而是一遍遍自己确认。这份"责任心"是它可靠性的来源：前面那个缺失的 TaskCard，就是它自己读文件时发现的。

但这里有一个我设计时没完全预料到的现象。我的引擎里有一个 idle 机制：当一个成员输出纯文本、不再调用工具时，它自动进入阻塞、暂停消耗。可 Manager 因为一直在调用工具，从不输出纯文本，所以**从不进入 idle**。它不是没事做，而是在持续确认——这是一种结构性的忙碌，恰好绕过了 idle 的触发条件。

这带来一个真实的成本问题。并行让两个 Operator 同时生产，收益是实打实的；但 Manager 的监督成本也随任务时长线性增长。尤其 read_file 会把文件内容读进上下文——62 次 read_file 读入的信息量，token 消耗可能比调用次数表面显示的更高。六分钟的短任务，这笔开销无所谓；可如果是一个半小时、两小时的长期任务，Manager 全程盯着的 token 成本就会累积到不可忽视。

我把它写出来，因为这是这个组织真实的代价之一：**可靠性不是免费的，它要靠主动监督去换；而主动监督本身要花钱。** 值不值，取决于任务时长和 token 成本的比重——这是我在持续想的问题，也是这个架构接下来要平衡的东西。

## 九、结论：协同是怎么发生的

回看这五幕，协同并不是靠"成员之间频繁聊天"发生的。恰恰相反，它是在**最少量的沟通**下发生的：

- **前置契约，胜过频繁沟通。** Manager 在派发前就把依赖关系、接口签名、文件归属定死了。正因为前面把边界清干净了，后面才不需要边做边反复对。
- **主动交接，胜过等待被问。** 004 没人要求，主动把接口送给下游。真正高效的协同里，信息是"推"给需要的人，而不是等人来"拉"。
- **闭环反馈，胜过单向汇报。** 003 不只为 Manager 服务，它还给 004 回了集成确认。你给过我接口，我告诉你结果——协同由此形成闭合。
- **主动监督，胜过被动等待。** Manager 不等汇报，自己读文件发现了缺口并补上。组织的可靠性，来自有人主动盯着，而不是指望每个人都自觉。
- **稀疏而精准，才是好通信。** 5 条消息换来 25 个零冲突的文件。通信的价值不在数量，在每条消息是否正好解决了对方的某个需要。

一句话总结：**这个组织之所以协同得干净，不是因为它聊得多，而是因为它在对的时候，对的人，传递了对的信息。** 契约、交接、闭环、监督——四件事，五条消息，一次完成。
