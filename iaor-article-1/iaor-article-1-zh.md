# 智能与代理之下：Intelligence Agent Organization Runtime（IAOR）是什么

**作者**: W.Y.
**日期**: 2026-08-12

---

> 我一直在做一个把多个独立 Agent 组织成团队的运行时——IAOR（Intelligence Agent Organization Runtime）。它第一次真正跑通一次协同实验之后，我决定把它讲清楚。这一篇先给它一个定义；后面几篇，是我在翻实验数据时陆续发现的东西。

## 一、定义：智能与代理是两层

先做一个定义。

同一个大模型，配不同的角色设定、不同的工具集、不同的工具组装与调用方式，会变成行为完全不同的独立 Agent。同一个模型，在 A 公司的 Agent 上表现得像一个严谨的工程师，在 B 公司的 Agent 上表现得像一个随和的助手，在你自己的 Agent 上又是另一个样子。

基于这个现象，我区分两层：

```
智能（Intelligence）——模型本身的能力。本质的、可复用的、共享的。
     ↓ 被"代理"
代理（Agent）——把智能"代理"成某个角色的载体。绑定某个模型，
    配上特定的 prompt 设定、工具集、工具的组装与调用方式。
```

一个 **Intelligence**（智能）可以被多个 **Agent**（代理）以不同方式代理；每个 Agent 因此继承了同一份智能的能力，却表现出不同的行为、语言、能力。**Agent 并不是孤立的——它背后永远共享着某一层 Intelligence。**

这个现象不是我发明的，它客观存在。每家在做 Agent 的公司——包括我自己——都在实践它：同一个模型，被不同的 prompt、不同的工具集、不同的组装方式"代理"成不同的 Agent。

我之所以把"Intelligence"和"Agent"分开命名，是因为这两个词在 IAOR 里指代不同的东西，下面会说明。

## 二、什么是 IAOR

既然"智能"和"代理"是两层，那么一个更准确的问题就浮出来了：

**当要把一群 Agent 组织成一个协作的团队时，组织的到底是什么？**

答案不是一堆孤立的 Agent。所组织的，是**代理了某个模型的智能体**——是那些背后共享着 Intelligence 的 Agent。把它们组织起来的运行时，就是：

**Intelligence Agent Organization Runtime（IAOR）**

- **Intelligence（智能）**——本质，模型的能力，可复用、可共享
- **Agent（代理）**——把智能代理成具体角色的载体
- **Organization（组织）**——把多个代理了智能的 Agent 组织起来
- **Runtime（运行时）**——承载这一切、能真实运行的基础设施

我之所以把"Intelligence"放在最前面，不是修辞，而是因为这个分层才是理解整个品类的起点：**你组织的不是黑盒 Agent，而是"代理了智能的 Agent"。**

## 三、Agent 之下，我看到的空白层

就我目前看到的技术栈现状，我认为这里有一个缺口。

```
┌───────────────────────────────────────────────┐
│  应用层                                         │
│  Codex, QoderWake, 杏林泛舟, Agent 365 等      │
├───────────────────────────────────────────────┤
│  ── 我认为缺失的一层：IAOR ──                 │
├───────────────────────────────────────────────┤
│  编排框架层                                     │
│  CrewAI, LangGraph, AutoGen                    │
├───────────────────────────────────────────────┤
│  模型路由层                                      │
│  Fugu, LiteLLM, Portkey                        │
├───────────────────────────────────────────────┤
│  操作系统层                                      │
│  ANOLISA, Step AOS, Linux, macOS               │
└───────────────────────────────────────────────┘
```

2026 年，这个行业有两股主流力量，但在我看来，都还没有明确地定义"组织"这一层：

**一股是互联标准。** 2026 年 5 月，中国发布了《人工智能 智能体互联》（GB/Z 185）系列国家标准，配套开源了 AIP（智能体互联协议）、发放了智能体身份码。它解决的是**接口层**的问题——不同厂家的 Agent 怎么互相"认识"、怎么"说话"、怎么按统一协议互通。它定义的是通信的"交通规则"。

**另一股是行业应用。** 一些厂商在标准之上做垂直落地，比如生命科学领域的杏林泛舟 AI 2.0，把合规检查、药物警戒等拆成多个业务智能体按标准互联。它解决的是**某个具体领域**的问题——药企怎么用多智能体提效。

但这两股力量，在我看来都没有正面回答那个更本质的问题：**当一群 Agent 要组成一个真正协作的组织时，谁来定义它们的结构、角色、通信、治理和记忆？**

- 互联标准管的是"Agent 之间怎么认识、怎么说话"——它不定义 Agent 如何被组织成团队
- 行业应用管的是"某个领域怎么用多智能体"——它不提供通用的组织运行时
- 编排框架（CrewAI、LangGraph）管的是"一次任务的流程怎么编排"——它把 Agent 当流程节点，不是当组织成员

**我认为，"组织"这一层还没有被清晰地定义。**

一个 IAOR 不关心你的 Agent 用的是什么模型，不关心它执行什么任务。它关心的是：

- **结构**：Agent 如何组织成团队，层级关系是什么，通信链路怎么走
- **协调**：任务如何拆解、派发、追踪
- **治理**：每个 Agent 能做什么、不能做什么，边界在哪里
- **记忆**：组织作为一个整体知道什么，跨 Agent 生命周期不丢失
- **韧性**：当 API 挂掉、限流触发、网络断开时，组织如何应对
- **领域无关**：核心引擎是领域中立的，领域知识按需挂载，同一个引擎可以驱动编码团队、法律研究组或内容创作组

可以把它理解为 Kubernetes for agents。Kubernetes 不关心你跑的是什么应用——它关心调度、扩展、网络和容错。IAOR 不关心你的 Agent 在做什么任务——它关心它们如何被组织、如何通信、如何从故障中恢复。

## 四、架构：三个角色，四个系统

这套架构是反复试错的结果。它还在演进，但核心结构已经稳定到可以分享。

角色是空壳——它们定义的是职责和权限，不是能力。能力来自挂载到角色上的领域知识、可用的工具集以及绑定的模型。协调编码团队的 Manager 和协调法律研究的 Manager 共享同一套核心行为，区别只在挂载的知识不同。

### 三个角色

**Director**——最高管理者。Director 站在组织之外，拥有全局视角，通过自然语言与用户交互。它监控组织状态、汇报异常、分析问题、执行用户决策，可以创建或销毁 Manager/Operator、调整策略、在必要时介入干预。*（目前 Director 已加入架构设计，完整的三层协同链路仍在开发中。）*

**Manager**——协调者。接收高层任务，拆解为子任务，创建具备相应能力的 Operator，分派工作，追踪进度，将结果存入 Archive。Manager 可以递归管理其他 Manager。

**Operator**——执行者。每个 Operator 有明确的能力边界（工具集、读写权限、模型绑定），自主决定如何完成分配的任务。它理解意图，自己决定执行路径。

### 四个系统

**Policy**——治理层。定义每个 Operator 在什么条件下可以做什么，动态可覆盖，可升级到 Director 审批。

**Channel**——通信基础设施。Operator 和 Manager 通过 Channel 通信而非直接函数调用，支持消息路由、广播和审计日志。

**Archive**——组织记忆。每个任务结果、每个决策、每个错误都存入 Archive，形成可查询的结构化知识库。

**Selector**——模型选择策略。根据能力需求、延迟敏感度、成本约束、历史成功率评估任务，选择最优模型，并自我优化。

## 五、证明它在跑：一次真实实验

我在一个自研引擎上实现并跑通了一系列实验。

### 核心实验

一个 **1 Manager + 2 Operator** 的团队，根据一份产品简报实现了一个 TaskFlow 看板应用。这是一次真实的开发任务，有真实的构建要求。

**一个前提必须先说清楚。** 这里的三个成员——Manager 和两个 Operator——各自持有一条独立的 LLM API Key。这不是一个单一大模型在内部并发派生出多个子代理，而是三个真正独立的成员，各自连着一条模型，被同一个运行时组织成一个团队。

**6 分 26 秒内发生了什么：**

| 指标 | 结果 |
|------|------|
| LLM 调用——Manager | 25 |
| LLM 调用——Operator 003（前端） | 23 |
| LLM 调用——Operator 004（基础设施） | 18 |
| **LLM 调用总计** | **66** |
| 产出文件 | 25 个源文件（5 基础设施 + 20 前端） |
| 执行方式 | 两个 Operator 并行 |
| 文件冲突 | 0 |
| `npm run build` | 通过，53 modules，零错误 |
| 人工介入 | 0 |

66 次调用换来 25 个文件、零冲突。这个数字是高是低，留给你自己判断。工作过程中，两个 Operator 也有过一次直接的相互对接——基础设施 Operator 把自己的完整接口文档直接交给了前端 Operator，没有经过 Manager。为什么这个组织值得多花这一点点调用、那一次直接对接又意味着什么，正是接下来几篇要展开的。

## 结语

这篇只想说一件事：在"智能"与"代理"之下，还缺着一个"组织"层。

单个 Agent 再强，也只是一个人；可当你想把一群真正独立的、各自连着一条模型的 Agent，组织成一个能协作的团队时，谁来定义它们的结构、角色、通信、治理和记忆？在我看来，目前还没有清晰的答案。IAOR 就是我给这个缺失层的回答。

而且它不是概念——它已经跑起来了：三个各自持有一条独立模型连接的成员，被一个运行时组织成一个团队，6 分 26 秒、25 个文件、零冲突。这个组织为什么值得，以及它能做出哪些单个 Agent 做不出的事，是接下来的文章要回答的。
